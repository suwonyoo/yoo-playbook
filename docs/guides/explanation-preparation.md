# 구현과 판단을 설명하는 연습

## 서술형 대비 키워드·작업 기록·자기 설명 가이드

SK하이닉스 AI 해커톤 2026 사전 준비용 · 2026-10-31 검토

좋은 설명은 구현한 기능, 선택 이유, 직접 확인한 결과가 서로 맞는 설명이다. 기술 용어를 많이 쓰는 것보다 실제로 무엇을 했고 어디까지 확인했는지를 정확히 말하는 편이 중요하다.

이 자료는 시험 전에 읽고 연습하는 자료다. **실제 후속 서술형에서는 AI와 복사·붙여넣기를 사용할 수 없다.** 문제를 이 도구에 전달해 답변을 생성하는 용도가 아니다. 공식 답안·채점 기준·예상 문제집도 아니다.

사용자가 사전 체험에서 보았다고 설명한 두 질문 유형을 출발점으로 삼았다. 실제 문항은 제출물과 작업 기록에 따라 달라질 수 있다.

## 1. 무엇을 기록해야 설명할 수 있는가

과제가 끝난 뒤 모든 판단을 기억해서 복원하려 하면 실제로 확인하지 않은 내용을 섞기 쉽다. 작업 중 중요한 사건이 생길 때 짧게 기록한다.

| 사건 | 남길 정보 | 설명할 수 있게 되는 것 |
|---|---|---|
| 요구사항 확인 | 근거·성공 조건 | 어떤 문제를 해결했는가 |
| 설계 선택 | 대안·선택·이유·단점 | 왜 이 방법을 골랐는가 |
| AI 요청 | 목적·제안·수정 여부 | AI를 어떻게 활용했는가 |
| 테스트 | 입력·기대·실제·판정 | 어떻게 맞는지 확인했는가 |
| 오류 수정 | 재현·원인·변경·재검증 | 실패에서 무엇을 바꿨는가 |
| 미완료 | 범위·영향·다음 행동 | 결과의 한계를 아는가 |

### 네 가지를 구분

사실: 파일이나 실행 결과로 확인할 수 있는 내용.

가정: 아직 확인하지 않았지만 작업을 진행하기 위해 정한 조건.

판단: 대안 중 어떤 것을 선택했고 왜 선택했는지.

관찰: 특정 입력·상황에서 직접 본 결과.

“AI가 맞다고 했다”는 관찰이나 검증 결과가 아니다. “코드를 읽어 보았다”와 “실행해 확인했다”, “AI가 테스트했다”와 “내가 Browser를 조작했다”도 구분한다.

### 설명의 기본 연결

목적 → 내가 구현한 동작 → 선택 이유 → 확인 방법과 결과 → 한계.

모든 질문에 이 다섯 항목을 똑같이 길게 쓰는 것은 아니다. 질문이 요구하는 부분부터 답하고 그 주장을 지지하는 사례를 붙인다.

## 2. 핵심 키워드 지도

키워드는 실제 행동을 떠올리는 표지다. 단어만 나열하지 말고 입력·파일·검증 사례에 연결한다.

| 키워드 | 함께 말할 구체적인 내용 |
|---|---|
| 사용자·업무 목적 | 누가 어떤 결정을 하도록 돕는가 |
| 핵심 흐름 | 어떤 입력이 어떤 처리 후 어떤 결과가 되는가 |
| 수용 기준 | 무엇을 보면 요구사항을 만족했다고 판단하는가 |
| 제약 | 시간·제공 데이터·스택·환경 중 실제 제한 |
| 대안·트레이드오프 | 선택한 장점과 감수한 단점 |
| 가설·재현 | 어떤 조건에서 문제가 생겼는가 |
| 정상·경계·오류 | 일반 입력, 한계값, 잘못된 입력에 대한 결과 |
| 기준선·검산 | 비교할 단순 방법 또는 수기 계산 |
| 데이터 품질 | 결측·중복·단위·기간·분모·조인 기준 |
| 재현성 | 같은 파일·명령·조건으로 다시 확인 가능한가 |
| 직접 확인 | 내가 수행한 행동과 실제 관찰 |
| 한계·영향 | 못 한 일과 사용자에게 생기는 영향 |

### 과제 유형별 보충

웹 과제: 상태 갱신, 입력 검증, 저장 범위, 오류 복구, 접근성.

데이터 과제: 집계 기준, 누락 처리, 키 유일성, 분모, 데이터 누출.

추천·예측: 기준선, 평가 지표, 검증 분할, 잘못된 예측의 비용.

문서·운영 개선: 대상 독자, 실행 가능한 절차, 예외 조건, 결과 확인.

사용하지 않은 기술을 전문성 표현용으로 끼워 넣지 않는다. 예를 들어 규칙으로 점수를 매겼다면 학습 모델이라고 부르지 않는다. 분산 처리하지 않았다면 “병렬 최적화”라는 말로 포장하지 않는다.

## 3. 핵심 동작과 확인 방법 설명

사용자가 전달한 사전 체험 질문 유형: “구현한 서비스의 핵심 동작과 이를 확인할 방법.” 실제 문항의 표현·범위는 달라질 수 있다.

### 답변 뼈대

“이 서비스는 [사용자]가 [목적]을 달성하도록 돕습니다. [입력]을 받으면 [핵심 처리]를 수행해 [결과]를 보여줍니다. [실행 경로와 행동]으로 확인할 수 있고, [테스트 입력]에서 [기대 결과]가 나오는지 보면 됩니다. [실제로 확인한 결과]를 확인했으며, [남은 한계]가 있습니다.”

대괄호는 자신의 사실로 채우는 사고 틀이다. 실제 서술형 답안에 그대로 붙여 넣거나 없는 내용을 채워서는 안 된다.

### 가상 연습 예시: 지역별 요청 집계

“지역별 요청 수를 비교하는 도구를 설계했습니다. CSV를 읽어 지역별로 묶고, 선택한 지역의 건수와 목록을 함께 표시하는 흐름입니다. 확인하려면 작은 CSV를 넣고 지역을 바꾼 뒤 수기 집계와 숫자가 일치하는지 비교합니다. 예를 들어 A 지역 세 행과 B 지역 한 행이면 각각 3과 1이 나와야 합니다.”

이 예시는 검증 절차의 설명이다. 실제로 실행한 경우에만 이어서 관찰 결과를 말할 수 있다. 실행하지 않았다면 “아직 실행 확인은 하지 않았다”고 구분한다.

### 빠지기 쉬운 부분

“검색과 필터가 있습니다”는 기능 목록이다. 어떤 조건을 입력하고 결과가 어떻게 달라지는지까지 적어야 확인 가능한 설명이 된다. “잘 됩니다” 대신 실제 사례를 쓴다. 실행 포트와 경로가 필요한 질문이면 자신이 사용한 값을 정확히 적는다.

저장 기능은 범위를 밝힌다. 메모리, 브라우저 저장, 서버 파일·DB는 유지되는 조건이 다르다. 새로고침만 확인했다면 서버 재시작 후에도 남는다고 단정하지 않는다.

## 4. AI에게 묻고 직접 확인한 내용

사용자가 전달한 두 번째 질문 유형: “AI에게 물어보고 직접 확인한 것들.” 여기서는 요청한 목적과 자신의 검증·판단을 연결한다.

### 답변 뼈대

문제/의문 → AI에게 맡긴 일 → 제안 내용 → 내가 확인한 방법 → 채택·수정·거절 → 결과.

| 약한 설명 | 구체화할 질문 |
|---|---|
| AI에게 코드를 짜 달라고 했다 | 어느 기능이며 성공 기준은 무엇이었나? |
| AI가 오류를 고쳤다 | 어떤 입력으로 재현했고 수정 후 어떻게 확인했나? |
| 결과를 확인했다 | 코드 읽기, 테스트 실행, 화면 조작 중 무엇인가? |
| AI와 협업했다 | 제안을 그대로 썼나, 왜 바꾸거나 거절했나? |

### 가상 연습 사례 A: 계산 제안 수정

AI에게 그룹별 성공률 집계 방법을 물었다고 가정한다. 제안이 그룹 비율의 평균이었다면, 그룹 크기가 다른 작은 표로 전체 성공 건수/전체 건수와 비교한다. 업무 목표가 전체 성공률이라면 후자를 선택하고 그 이유를 기록한다. 단순히 “AI 오류를 잡았다”보다 어떤 정의가 달랐는지 설명한다.

### 가상 연습 사례 B: UI 상태 확인

필터 기능 구현을 맡긴 뒤 사람이 제공 Browser에서 지역을 바꾸고 표·요약 숫자가 함께 바뀌는지 본다. 코드상 필터가 존재하는 것과 화면 상태가 갱신되는 것은 별도 확인이다. 실제 관찰한 입력과 결과를 기록한다.

### 직접 확인의 범위

AI가 실행한 테스트 로그를 읽었다면 “AI가 테스트를 실행했고 나는 결과와 사례를 확인했다”라고 말한다. 본인이 직접 명령을 실행했거나 화면을 조작한 경우에는 그 행동을 구체적으로 적는다. 둘을 하나의 경험으로 합치지 않는다.

## 5. 선택·대안·판단 근거

판단 설명은 “선택 A가 항상 좋다”가 아니라 “이 과제의 조건에서는 A를 선택했고 B의 장점은 포기했다”라는 구조다.

### 짧은 판단 기록

상황: 무엇을 결정해야 했는가.

대안: 현실적으로 가능한 두 방법은 무엇인가.

선택: 어떤 방법을 택했는가.

이유: 시간·요구사항·정확성·데이터·설치 비용 중 실제 조건과 어떻게 연결되는가.

단점과 전환 조건: 무엇이 부족하며 어떤 변화가 있으면 다른 방법을 택할 것인가.

### 가상 예시: 저장 방식

연습 과제가 한 브라우저의 임시 작업 보존만 요구한다면 브라우저 저장을 선택할 수 있다. 서버 DB는 여러 기기·사용자 간 공유에 장점이 있지만 설치·연결·마이그레이션 비용이 든다. 실제 요구가 공유 저장이라면 이 선택은 맞지 않는다. 선택 이유와 적용 범위를 함께 말해야 한다.

### 가상 예시: 새 프레임워크 도입

기존 프로젝트가 실행되고 필요한 기능을 지원한다면 스택을 유지해 검증 시간을 확보할 수 있다. 반대로 필수 요구가 기존 구조로 충족되지 않으면 변경이 필요하다. “시간이 없어서”만 쓰기보다 확보한 시간으로 어떤 필수 검증을 했는지 연결한다.

### 단정하지 말 것

“효율적이다”에는 무엇의 효율인지가 필요하다. 개발 시간, 실행 시간, 메모리, 유지보수성은 다르다. 측정하지 않은 성능 향상은 숫자로 쓰지 않는다. 대안을 실제로 비교하지 않았다면 검토한 범위를 정확히 말한다.

## 6. 실패·수정·검증·한계

오류 경험은 실패 자체보다 관찰을 통해 판단을 바꾼 과정을 설명할 때 유용하다. 실제로 없었던 오류를 좋은 이야기로 만들지 않는다.

### 오류 설명의 연결

증상 → 재현 입력 → 원인 후보 → 원인을 구분한 확인 → 수정 → 원래 입력 재검증.

가상 예: “결과가 두 배로 집계되는 현상이 있었다”면 조인 전후 행 수와 키 중복을 확인한다. 중복 키에 따른 행 증가가 원인이었는지 관찰하고, 처리 규칙을 바꾼 뒤 원래 입력과 정상 입력을 다시 비교한다.

### 검증을 설명할 때

| 구분 | 설명할 내용 |
|---|---|
| 정상 | 대표 사용 흐름에서 기대 결과 |
| 경계 | 빈 목록·0·최댓값·날짜 경계 중 관련 사례 |
| 오류 | 잘못된 형식·실패 상황에서 사용자 대응 |
| 회귀 | 수정 전 정상 동작이 유지되는지 |
| 한계 | 실행하지 못한 환경·크기·조건 |

### 한계는 영향까지

“시간이 부족해 미완성”보다 “대용량 파일에서 응답 시간을 확인하지 못했으므로 실제 운영 규모의 성능은 보장하지 않는다. 다음에는 크기를 늘린 입력으로 측정하겠다”가 구체적이다. 다만 그 한계도 자신의 실제 구현과 관련 있어야 한다.

미구현과 미검증을 구분한다. 기능이 없으면 미구현이다. 구현했지만 실행해 보지 못했으면 미검증이다. 일부 사례만 확인했다면 부분 확인이다. 셋을 모두 “완료”로 묶지 않는다.

## 7. 작업 중 AI 출력 형식

과제 수행 중 AI와 문서를 작성할 수 있다는 안내를 활용하되, 모든 응답을 길게 만들지는 않는다. 기능·판단·검증이 바뀔 때 아래 정보가 남도록 요청한다. 실제 후속 서술형 단계에서 사용하는 형식이 아니다.

### 기본 결과 형식

```text
변경: 요구사항 ID와 실제 변경 위치
이유: 선택한 방법과 핵심 근거
검증: 실행 명령/수동 절차, 입력, 기대값, 실제 결과
직접 확인: 사람이 수행한 행동 또는 확인 대기
한계: 미구현/미검증 범위와 영향
다음: 남은 필수 행동
```

### 바로 쓸 요청

> 기능을 마칠 때마다 변경·이유·검증·직접 확인·한계를 간단히 알려줘. 명령 결과를 확인한 경우만 통과라고 쓰고, 내가 아직 조작하지 않은 UI는 확인 대기로 남겨줘. 실제 판단과 검증만 기록 파일에 반영해줘.

### 업무 질문에 대한 출력

업무 의미가 애매하면 “질문 / 현재 가정 / 답에 따라 바뀌는 구현”으로 정리한다. 단순한 승인 질문을 늘리는 대신 구현 방향에 영향을 주는 내용을 묻는다. 아직 답을 받지 못했다면 가정과 영향이 기록되어야 한다.

### 코드 리뷰에 대한 출력

발견한 문제, 재현 조건, 영향, 파일 위치, 수정 방향을 받는다. “전체적으로 좋다”는 말보다 구체적 결함과 확인하지 않은 범위를 받는 편이 유용하다. 문제를 찾지 못했다면 실제로 읽은 범위와 실행한 검증을 남긴다.

### 토큰과 기록 균형

매 응답에 긴 보고서를 재생성하지 않는다. 중요한 변경만 갱신하고 최종 문서는 실제 기록에서 추린다. 로그와 파일을 참조해 과거 결과를 반복 복사하지 않는다.

## 8. 기록 템플릿과 증거 연결

공식 제출 양식이 있으면 그 형식을 사용한다. 이 저장소의 파일명은 작업을 돕는 예시이며 필수 제출명으로 확인된 것이 아니다.

| 파일 | 기록 내용 | 필요한 시점 |
|---|---|---|
| requirements.md | 필수조건·근거·검증 방법 | 과제 시작과 조건 변경 |
| decisions.md | 대안·선택·이유·단점 | 중요한 선택 직후 |
| collaboration.md | AI 요청·내 판단·직접 확인 | 결과를 바꾼 협업 사건 |
| verification.md | 입력·기대·실제·근거·판정 | 테스트·수동 확인 직후 |
| limitations.md | 미구현·미검증·영향 | 범위 결정과 제출 전 |
| handoff.md | 현재 상태·다음 행동 | 세션 전환·긴 작업 정리 |

### 한 줄에서 시작

“R-001 집계 → calculate.py → V-001 작은 표 검산 → 로그 경로 → 대용량 미검증”처럼 연결한다. 파일명과 값은 실제 프로젝트에 맞춘다. 기록 길이보다 각 주장의 근거를 다시 찾을 수 있는지가 중요하다.

### 수동 확인 기록

수행자, 입력, 누른 버튼, 관찰한 결과, 기대와의 차이를 남긴다. 사람이 아직 결과를 알려주지 않았다면 미확인으로 둔다. 실제 시험에서 금지된 캡처·자동 조작을 증거 수집 수단으로 쓰지 않는다.

### 사후 정리

기록을 나중에 정리했다면 정리 시각과 실제 작업 시점을 구분한다. 기억이 불확실한 선택 이유를 확정 사실로 바꾸지 않는다. 원래 로그가 없으면 “기록 없음/기억 불확실”을 명시한다.

하네스가 만든 실행 로그도 읽고 의미를 확인해야 한다. 종료 코드 0, 테스트 수, 표의 계산 결과, 화면의 실제 동작은 서로 다른 수준의 증거다.

## 9. 추가 연습 질문

아래는 실제 출제를 예측한 목록이 아니다. 자신의 작업을 이해했는지 확인하는 사전 연습 질문이다.

1. 사용자가 가장 먼저 해야 하는 행동은 무엇이고 어떤 결과를 얻는가?
2. 반드시 구현해야 하는 조건과 선택 기능을 어떻게 구분했는가?
3. 제공 데이터에서 가장 먼저 확인한 품질 문제는 무엇인가?
4. AI의 제안 중 그대로 쓰지 않은 것이 있다면 왜 바꿨는가?
5. 선택한 구현 방식의 가장 큰 단점은 무엇인가?
6. 실제 오류를 어떻게 재현하고 원인을 좁혔는가?
7. 어떤 검증이 어떤 요구사항을 확인했는가?
8. 빌드 성공 외에 동작을 어떻게 확인했는가?
9. 시간이 더 있었다면 어떤 위험부터 검증하겠는가?
10. 다른 사람이 같은 결과를 확인하려면 어떤 파일·명령이 필요한가?
11. 문서의 설명과 실제 구현이 다를 가능성이 있는 부분은 어디인가?
12. 질문의 전제가 실제 구현과 다르면 어떻게 정확히 설명하겠는가?

### 연습 방법

질문 하나를 골라 자료를 보지 않고 답한다. 그 후 자신의 코드·기록과 비교해 사실이 맞는지 확인한다. 사전 연습에서는 AI에게 피드백을 받을 수 있지만 먼저 자신이 답해야 부족한 부분을 알 수 있다.

피드백은 사실성, 구체적 증거, 이유와 결과의 연결, 한계의 정확성으로 받는다. 이것은 연습용 기준이며 공식 채점표가 아니다.

답변에 없는 경험을 추가해 더 그럴듯하게 만드는 대신, 구현이나 기록의 빈 부분을 찾아 실제로 확인하는 연습을 한다.

## 10. 5분 답변 연습과 최종 점검

제공 안내는 문항당 5분, 총 6문항을 설명한다. 실제 화면의 안내가 우선이며 이전 문항으로 돌아갈 수 없다는 점을 기억한다. 이 시간 배분은 사전 연습용 예시다.

| 시간 | 할 일 |
|---|---|
| 0:00~0:30 | 질문이 요구하는 핵심과 전제 읽기 |
| 0:30~1:00 | 사용할 실제 사례 하나와 결론 정하기 |
| 1:00~3:30 | 행동·이유·증거를 연결해 직접 작성 |
| 3:30~4:30 | 사실·숫자·구현 범위·한계 점검 |
| 4:30~5:00 | 질문에 답했는지 확인하고 제출 |

### 제출 전 다섯 질문

내가 실제로 한 행동인가? 질문의 핵심에 먼저 답했는가? 구체적인 입력이나 결과가 있는가? AI가 한 일과 내가 확인한 일을 구분했는가? 모르는 부분과 한계를 정직하게 표시했는가?

### 질문의 전제가 다를 때

“해당 기능은 구현하지 않았고 실제로는 A 방식으로 처리했다”처럼 차이를 먼저 밝힌다. 없는 기능을 질문에 맞춰 꾸며 설명하지 않는다. 실제로 구현한 동작과 그 범위를 이어서 설명한다. 플랫폼 문항 오류라면 안내된 신고 경로를 따르되 타이머가 멈춘다고 가정하지 않는다.

### 작업 종료와 응시 종료

과제 파일 확정은 최종 응시 완료와 다르다. 후속 서술형과 마지막 처리까지 완료 화면을 확인한다. 실제 서술형에서는 이 AI를 사용하거나 답안을 붙여 넣지 않고, 자신의 이해를 바탕으로 직접 입력한다.

근거: 브리프 1쪽, 상세 가이드 4~5쪽. 화면 예시의 문항 수와 준비 시간은 실제 안내와 구분한다.

## 11. 주의할 표현과 출처

| 피할 표현 | 사실에 맞게 바꾸는 방향 |
|---|---|
| 완벽하게 검증했다 | 어떤 사례·환경을 확인했고 무엇은 못 했는지 |
| AI가 다 만들어줬다 | 맡긴 범위, 채택·수정한 부분, 직접 확인 |
| 성능이 크게 좋아졌다 | 측정한 지표·조건·전후 값, 없으면 측정 안 함 |
| 오류가 없다 | 실행한 사례에서 오류가 재현되지 않았음 |
| 실시간 분석이다 | 실제 갱신 주기와 트리거 설명 |
| 머신러닝으로 추천했다 | 실제로 학습했는지 규칙 점수인지 구분 |
| 저장된다 | 메모리·브라우저·서버와 유지 범위 |
| 사용자 친화적이다 | 입력 라벨·오류 안내·확인한 사용 흐름 |

### 이 자료의 근거

제공된 `1_시험_필수확인사항_브리프.pdf` 1쪽: 후속 서술형의 AI·복사 붙여넣기 제한, 문항 수와 시간.

제공된 `3_사전_체험_및_응시환경_상세_가이드.pdf` 3~5쪽: 계획·협업 문서, 판단·근거·검증·한계 기록, 제출물 확정, 질문과 실제 구현의 차이 설명, 최종 완료.

사용자가 전달한 사전 체험의 두 질문 유형: 핵심 동작과 확인 방법, AI에게 묻고 직접 확인한 내용. 실제 출제 전체를 확인했다는 뜻은 아니다.

질문 예시, 답변 뼈대, 키워드 지도, 5분 배분과 피드백 기준은 이 준비 도구에서 새로 작성한 연습안이다. 가상 사례는 자신의 경험이나 실행 결과로 사용하지 않는다.
